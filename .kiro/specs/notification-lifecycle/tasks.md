# Implementation Plan

> 実装順の要点: 契約と識別規則 (群1) を先に固め、Session の後始末 (群2) → シグナル配線 (群3) の順に積む。
> 群1の 1.3 (プロトコル置換) はモック5クラスと LaunchGuard の追随を同一タスクで行う —
> 分けるとその間ビルドが壊れるため。

- [ ] 1. Foundation: 契約と識別規則

- [ ] 1.1 (P) 通知の識別規則を純粋関数として定義する
  - group ありの識別名を「符号化した group + 区切り + ユニーク値」、group なしをユニーク値単体として生成する
  - group 置換の走査に使う接頭辞を同じ規則から導出する。識別名の組み立てをこの単一ソース以外に書かない
  - 生成した識別名が常に自 group の接頭辞に一致し、先頭部分が重なる別 group (`a` と `ab`、`a` と `a#b`) の接頭辞には互いに一致しないこと、group なしの識別名がいかなる接頭辞にも一致しないことを不変条件とする
  - `#` や非 ASCII を含む group、および符号化結果が接頭辞関係になる組 (`abc` と `abcd`) を含めて、上記の不変条件が単体テストで固定される
  - _Requirements: 1.4, 1.5_
  - _Boundary: NotificationIdentity_

- [ ] 1.2 (P) 結果種別 canceled の出力契約を追加する
  - 結果の列挙に `canceled` を追加し、JSON 表現を `{"result":"canceled"}` とする (種別固有フィールドなし)
  - 終了コードの対応に canceled → 5 を追加し、定数として既存の定数群と同じ場所に定義する
  - `--print result` の値は `canceled`、他フィールド (action / actionIndex / text) は値なしとする
  - `--exit-code` 未指定時は既存どおり 0 になる (既存の方針分岐が自動的に満たすことを確認する)
  - 既存5種の結果の JSON・終了コードが不変であることを回帰テストで固定し、予約コード (1, 2) と使用済みコード (3, 4, 10+) に canceled が衝突しないことをテストで固定する
  - _Requirements: 3.1, 3.2, 3.3, 3.4, 3.5, 3.6, 3.7, 1.6_
  - _Boundary: Output_

- [ ] 1.3 通知センター抽象の配信済み一覧を識別名の列へ置き換える
  - `getDeliveredNotifications` を、識別名の文字列列を返すメソッドへ置き換える (実アダプタが通知 → 識別名の写像を担う)
  - 掃除処理 (LaunchGuard) を新メソッドへ追随させる。識別名しか使っていないため挙動は等価
  - テストのモック5クラスを新メソッドへ追随させる。モックが任意の識別名列を返せるようになり、これまで SDK 制約 (通知オブジェクトをテストから構築できない) で空配列しか注入できなかった掃除の検証が、非空フィクスチャで可能になる
  - 既存の全テストが通り、掃除処理に「複数件の識別名が返った場合に全件削除される」テストが追加される
  - _Requirements: 1.3_
  - _Boundary: NotificationCenterClient, LaunchGuard_

- [ ] 2. Session の後始末の正確化

- [ ] 2.1 配信時の識別名採番と group 置換を走査方式へ変更する
  - 配信時に識別規則 (1.1) で自分の識別名を採番し、保持する
  - group 指定時は「配信済み一覧の取得 → 自 group の接頭辞に一致する識別名の抽出 → 削除 → 配信」の順で置換する
  - group 未指定時は既存の配信済み通知をいかなる契機でも削除の対象へ含めない
  - タイムアウト時の削除対象を、採番した自分の識別名のみとする
  - モックが返す識別名列 (自 group 2件 + 先頭部分が重なる別 group 1件 + group なし 1件) から自 group の2件だけが削除されることをテストで固定する
  - セッション A のタイムアウトが、モック上のセッション B の識別名を削除しないことをテストで固定する (修正対象のバグの回帰テスト)
  - _Depends: 1.1, 1.3_
  - _Requirements: 1.1, 1.2, 1.3, 1.4, 1.5_

- [ ] 2.2 キャンセルの確定と配信ガードを追加する
  - タイムアウトと対になるキャンセル入力 (`handleCancel`) を追加し、`canceled` として結果を確定する
  - 自分の通知の削除条件を「タイムアウト」から「タイムアウトまたはキャンセル」へ広げる
  - 結果確定済みの場合は配信を行わないガードを配信処理へ追加する (配信前キャンセル後に認可コールバックが届いても通知が出ない)
  - 一度きり確定の既存機構は変更しない。応答・タイムアウト・キャンセルの競合は先着が勝つ
  - キャンセルで自分の通知が削除されること、確定済み後のキャンセルが無視されること、キャンセル確定後の配信が行われないこと、未配信時のキャンセルが削除なしで確定することがテストで固定される
  - _Depends: 1.2, 2.1_
  - _Requirements: 2.1, 2.4, 2.5, 1.1_

- [ ] 3. シグナル配線

- [ ] 3.1 SIGTERM の受信を配線する
  - SIGTERM の既定動作を無効化し、main queue で通知を受けるシグナルソースを1箇所で保持する部品を新設する
  - 登録対象は SIGTERM のみとし、SIGINT には触れない
  - 通知送信の実行経路の冒頭 (認可要求より前) で登録し、キャンセル入力 (2.2) へ結線する
  - シグナルソースを保持しない限り受信しないことを部品の契約として明記する
  - テストプロセス自身への SIGTERM 送出 (`kill(getpid(), SIGTERM)`) で、注入したコールバックが呼ばれることをテストで固定する
  - _Depends: 2.2_
  - _Requirements: 2.5, 2.6, 2.7_
  - _Boundary: CancellationSignal, NotifyCommand_

- [ ] 4. 検証とドキュメント

- [ ] 4.1 キャンセルの一連の順序を結合テストで固定する
  - キャンセル確定 → 自通知の削除 → 出力 (JSON / `--print`) → 遅延 exit の順序を、モック連鎖 (Session → Emitter → ExitCoordinator) で検証する
  - `--exit-code` 指定時に exit 5、未指定時に exit 0 となることを同じ連鎖で確認する
  - 既存5種の結果の連鎖挙動が不変であることを合わせて確認する
  - 追加テストを含む全テストが通る
  - _Depends: 3.1_
  - _Requirements: 2.2, 2.3, 3.2, 3.3, 1.6_

- [ ] 4.2 README を追随させる
  - 結果種別の一覧へ `canceled` を追記する (en / ja 両方)
  - `--exit-code` の対応表へ canceled → 5 を追記する
  - SIGTERM による通知キャンセルの用途と使い方 (応答待ちプロセスへのシグナル送達で通知ごと片付く。`pkill -f <group文字列>` の例) を記載する
  - 記載内容が実装の挙動と一致し、en / ja の内容が揃っている
  - _Depends: 4.1_
  - _Requirements: 4.1, 4.2, 4.3_

- [ ] 4.3 GUI 依存部分の手動検証チェックリストを追記する
  - 通知表示中に `pkill -f <group>` → 通知センターから通知が消え、`canceled` が出力されること
  - 同一 group の通知を5分以内に2回出し、1回目のタイムアウト時刻を過ぎても2回目の通知が残っていること (修正前は消えていた)
  - 既存の手動検証ドキュメントへ2項目が期待結果つきで追記される
  - _Depends: 4.1_
  - _Requirements: 2.1, 2.3, 1.1, 1.2_

## Implementation Notes

- 実バイナリでの SIGTERM テストは、待機状態に到達するのにバンドル (通知許可) が必要なため自動化できない。シグナル受信の配線は自プロセスへの `kill(getpid(), SIGTERM)` (task 3.1)、経路全体はモック連鎖 (task 4.1) と手動検証 (task 4.3) で分担する
- 旧バージョンが配信した通知 (識別名 = 生の group) は新バージョンの走査で拾えないが、タイムアウト削除・sweep・クリックで解消する一過性の影響として許容する (design.md NotificationIdentity)
