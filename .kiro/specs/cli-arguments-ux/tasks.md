# Implementation Plan

> 実装順の要点: 起動経路の修正 (群3) を短縮フラグ (群4) より先に完了させる。
> 短縮フラグが入る前にコマンド種別の誤判定を閉じておかないと、`-t install` のような入力で
> バンドル外クラッシュの影響範囲が広がる。

- [ ] 1. Foundation: 共有部品と抽象の追加

- [x] 1.1 タイムアウト指定を秒数へ換算する共有部品を作る
  - 単位なしの数値を秒として解釈する (小数を許容し、既存の受理範囲を狭めない)
  - `h` / `m` / `s` を伴う指定と、それらの連結指定を合計秒数へ換算する
  - 解釈できない入力と、換算結果が正でない入力を区別せず失敗として返す
  - 単位の重複・順序入れ替えは合計値が定まるため受理する
  - Foundation のみに依存し、通知APIの型に触れない
  - `300` / `0.5` / `90s` / `5m` / `1h30m` の換算値と、`abc` / `-5` / `0` / `5x` / 空文字列の拒否が単体テストで通る
  - _Requirements: 4.1, 4.2, 4.3, 4.4, 4.5_

- [x] 1.2 (P) ファイルディスクリプタの端末接続を判定する共有部品を作る
  - 指定したディスクリプタが端末に接続されているかを返す述語を提供する
  - 標準入力・標準出力・標準エラーのいずれかが端末かを判定する関数を提供する
  - 判定の実体を1箇所に集約し、他のコンポーネントは述語を注入で受け取れるようにする
  - 述語を差し替えた単体テストで、3ストリームの組み合わせに対する判定結果が確認できる
  - _Requirements: 5.3, 12.1, 12.2, 13.1, 13.2_
  - _Boundary: TerminalDetection_

- [x] 1.3 (P) 通知許可の状態を読み取る手段を通知センター抽象へ追加する
  - 既存の抽象には許可を要求するメソッドしか無く、そのままでは診断のたびに許可ダイアログが出る
  - 許可状態を取得するだけの読み取り専用メソッドをプロトコルと実アダプタの双方へ追加する
  - 既存メソッドの挙動と、それを使う通知配信の経路は変更しない
  - モック実装から許可状態を注入でき、既存のテストがすべて通る
  - _Requirements: 15.4_
  - _Boundary: NotificationCenterClient_

- [ ] 2. 新規サブコマンドの追加

- [x] 2.1 (P) 補完スクリプトを出力するサブコマンドを作る
  - シェル名を引数に取り、ルートコマンドの補完スクリプトを標準出力へ書く
  - 受け付けるシェルを bash / zsh / fish の3種に限定し、それ以外は補完スクリプトを出さずにエラー終了する
  - 生成処理そのものは実装せず、引数パーサが提供する生成結果をそのまま出力する
  - 通知APIおよびAppKitを import しない
  - 3種のシェルそれぞれでスクリプトが出力され、未対応のシェル名が非0で拒否される
  - _Requirements: 8.1, 8.2, 8.3, 8.8_
  - _Boundary: CompletionCommand_

- [x] 2.2 (P) 孤児通知を明示的に削除するサブコマンドを作る
  - 既存の掃除処理から「削除して件数を返す」部分を切り出し、引数なし起動の経路と共有できる形にする
  - 引数なし起動の経路は件数を捨てて従来どおり終了する (既存の振る舞いを変えない)
  - 新しいサブコマンドは標準ストリームの接続状態によらず削除を実行する
  - 削除した件数を表示する。0件でも同じ形式で報告する
  - モックの通知センターに対して、削除対象の識別子がすべて渡り、件数が出力に現れることをテストで確認できる
  - _Requirements: 12.3, 12.4, 12.5_
  - _Boundary: SweepCommand, LaunchGuard_

- [x] 2.3 (P) 環境診断の項目収集を作る
  - 既定バンドルの有無とバージョン、プロファイルバンドルの一覧、実行中バイナリとの版の一致、PATH上のリンクの有無と指し先を診断項目として収集する
  - リンクのパス解決はインストーラが用いる環境変数と既定値を参照し、パス組み立てを重複させない
  - リンクの有無はリンク自体の属性で判定し、壊れたリンクを不在と誤判定しない
  - 各項目に正常・警告・異常・判定不能のいずれかの状態と、問題時に取るべき操作を持たせる
  - ファイル操作を注入したテストで、未インストール・版の不一致・リンク切れの各状況が対応する状態として収集されることを確認できる
  - _Requirements: 15.1, 15.2, 15.3, 15.6_
  - _Boundary: DoctorCommand_

- [x] 2.4 環境診断の整形と終了コードを作る
  - 収集した項目を人間可読の形式で表示する
  - 機械可読出力の指定に対応する
  - 警告または異常が1件以上あれば非0、なければ0で終了する。判定不能の項目は問題として数えない
  - 診断項目の配列を注入した単体テストで、終了コードと機械可読出力の構造が確認できる
  - _Depends: 2.3_
  - _Requirements: 15.7, 15.8, 15.9_

- [x] 2.5 環境診断へ通知許可の判定を組み込む
  - バンドル内で実行されている場合のみ、通知許可の状態を読み取って診断項目に加える
  - **許可を要求してはならない。** 要求すると診断のたびに許可ダイアログが出る。1.3 で追加した読み取り専用の手段のみを使う
  - バンドル外で実行されている場合は許可状態を判定不能として報告し、インストール案内で終了しない
  - 非同期コールバックの完了は、既存の掃除処理と同じセマフォとタイムアウトの方式で待つ
  - バンドル内外を模した注入により、許可済み・未許可・判定不能の3状態が診断結果に現れることを確認できる
  - _Depends: 1.3, 2.4_
  - _Requirements: 15.4, 15.5_

- [ ] 3. 起動経路の正確化

- [x] 3.1 新規サブコマンドを登録し、ルートコマンドの説明を整える
  - 補完・掃除・診断の3サブコマンドをルートコマンドへ登録する
  - ルートコマンドと既定サブコマンドに1行の説明を与える。説明の無いサブコマンドを残さない
  - すべての表示文言を英語で記述する
  - ルートコマンドのヘルプに、登録済みの全サブコマンドが説明付きで並ぶ
  - _Depends: 2.1, 2.2, 2.3_
  - _Requirements: 7.1, 7.4_

- [x] 3.2 コマンド種別の判定をコマンド解決の結果に基づく方式へ置き換える
  - 引数文字列の位置走査による判定を廃し、ルートコマンドの解決結果の型で種別を決める
  - 通知の配信および掃除を要求する種別、診断を要求する種別、通知APIに依存しない種別の3分類とする
  - 解決が失敗した場合も通知APIに依存しない種別として扱う
  - ヘルプ要求は失敗せずヘルプ用コマンドとして解決されるため、失敗の有無ではなく返った型で分類する
  - 解決処理を注入可能にし、各コマンド型と失敗ケースの分類を単体テストで網羅する
  - オプションの値がサブコマンド名と一致する引数が、サブコマンド指定として解釈されないことをテストで確認できる
  - _Requirements: 11.1, 11.2, 11.5, 8.4, 8.6_

- [x] 3.3 起動の分岐判定を再設計し、ヘルプ表示の分岐を追加する
  - 種別・バンドル内外・既定バンドルの有無・端末接続の有無を入力とする純粋関数として分岐を決める
  - 引数なしかつ端末接続ありならヘルプ表示、端末接続なしなら従来どおり孤児通知の掃除とする
  - 診断を要求する種別のみ、既定バンドルが未インストールでも案内で終了せず処理を継続させる
  - 通知APIに依存しない種別に対して引き継ぎや案内を返さないことを不変条件とする
  - 種別3種 × バンドル内外 × インストール有無 × 端末接続有無の組み合わせが単体テストで網羅される
  - _Depends: 1.2, 3.2_
  - _Requirements: 11.3, 11.6, 12.1, 12.2, 15.5_

- [x] 3.4 エントリポイントを新しい判定へ結線する
  - 種別の判定と分岐の決定をエントリポイントから順に呼び、決定に応じて処理を振り分ける
  - ヘルプ表示の分岐でルートコマンドのヘルプを標準出力へ書き、正常終了する
  - 種別の判定は通知APIの初期化より前に完了させる。判定処理は引数の解釈のみを行い、コマンドの実行は行わない
  - 判定の過程で引数の検証が実行される点に注意する。検証に副作用を持たせてはならない (4.4 の前提)
  - バンドル外の実バイナリに対し、オプションの値がサブコマンド名と一致する引数を与えても異常終了しないことを確認できる
  - _Depends: 3.3_
  - _Requirements: 11.3, 11.4, 12.1_

- [x] 3.5 バージョン不一致案内の表示条件を絞る
  - 案内の文言生成は純粋関数のまま維持し、表示するかどうかの判定を呼び出し側へ移す
  - 標準エラーが端末に接続されているときだけ案内を出す
  - 案内の有無が処理の成否と終了コードに影響しないことを維持し、標準出力を汚さない
  - 端末判定の述語を差し替えたテストで、非端末時に案内が出ず、終了コードが変わらないことを確認できる
  - _Depends: 1.2_
  - _Requirements: 13.1, 13.2, 13.3, 13.4_

> 群3の各タスクはいずれもエントリポイントの同一ファイルを変更するため、並列実行できない。
> 3.5 は判定対象が別だが、変更箇所が同居しているため `(P)` を付けない。

- [ ] 4. notify の引数受理の拡張

- [x] 4.1 頻用オプションに短縮形を追加する
  - タイトル・本文・プロファイル・アクションの4つに短縮形を与える
  - 短縮形と従来のロング形式を同一の意味として扱い、既存のロング形式をすべて引き続き受け付ける
  - アクションの短縮形の繰り返し指定が、従来と同じ並び順を構成する
  - 値の結合表記は有効化しない。有効化するとプロファイル指定の除去が不完全になり、4.2 の対策が破れる
  - 短縮形と長形式が同一の通知リクエストを生むことをテストで確認できる
  - _Depends: 3.4_
  - _Requirements: 6.1, 6.2, 6.3, 6.5_

- [x] 4.2 (P) プロファイル指定の除去対象へ短縮形を加える
  - 引き継ぎ先へ渡す引数から、プロファイル指定を長短4形態すべてで除去する
  - 除去が不完全だと引き継ぎ先で再びプロファイル解決が走り、プロセスが無限に自身を置き換える
  - 除去の網羅性が「値の結合表記を許可しない」前提に依存することをコード上に明記する
  - 長短4形態それぞれについて、除去後の引数列にプロファイル指定が残らないことをテストで確認できる
  - _Requirements: 6.6_
  - _Boundary: ProfileDispatch_

- [x] 4.3 タイムアウトの解釈を共有部品へ委譲する
  - 引数の変換処理から共有部品を呼び、失敗時は通知を配信せずに引数エラーとする
  - エラー文言に受理する書式を含める
  - 指定が無いときは従来どおり無期限に待つ
  - 単位付き指定が通知リクエストの秒数へ正しく反映され、不正な指定が配信前に拒否されることを確認できる
  - _Depends: 1.1, 4.1_
  - _Requirements: 4.1, 4.2, 4.3, 4.4, 4.5, 4.6_

- [x] 4.4 本文を標準入力から読み取れるようにする
  - 本文の値が単一のハイフンのとき、標準入力を終端まで読み取って本文とする
  - 読み取った内容の末尾の改行を取り除く
  - **読み取りは通知リクエストの組み立て時に行う。引数の検証時に行ってはならない。** 検証は起動ゲートの分類時と中間の引き継ぎ時にも実行されるため、そこで読むとプロファイル併用時に最終的な本文が空になる
  - 検証時に行ってよいのは、標準入力が端末に接続されているかの判定のみとする。端末なら読み取りを開始せずエラー終了する
  - 読み取り処理を注入したテストで、末尾改行の除去と、端末接続時のエラー終了が確認できる
  - _Depends: 1.2, 4.1_
  - _Requirements: 5.1, 5.2, 5.3, 5.4, 5.5_

- [x] 4.5 画像添付を配信前に検証する
  - 通知許可を要求する前に、指定パスの存在と読み取り可否を検証する
  - 添付として対応する画像形式を png / jpg / jpeg / gif の4種とし、拡張子の一致で判定する
  - 存在しない・読み取れない場合は対象パスを含む文言で、非対応形式の場合は対応形式を示す文言でエラー終了する
  - フレームワーク由来の内部エラー表現をそのまま表示しない。検証を通過した後の添付生成失敗にも同じ方針を適用する
  - 指定が無いときは添付に関する検証を行わない
  - 不正なパスと非対応拡張子が、通知を配信せず人間可読な文言で拒否されることを確認できる
  - _Depends: 4.1_
  - _Requirements: 9.1, 9.2, 9.3, 9.4, 9.5_

> 群4の 4.2 以外は通知送信サブコマンドの同一ファイルを変更するため、並列実行できない。
> ヘルプの使用例は 5.4 で追加するオプションを参照するため、群5の末尾 (5.5) に置いている。

- [ ] 5. 結果の出力契約の拡張

- [x] 5.1 出力方針と出力対象フィールドの型を定義する
  - 出力対象フィールドを結果種別・アクション名・アクション番号・返信テキストの4種に限定した列挙型として定義する
  - 引数として受け取れる型に適合させ、4種以外の値が引数解析の段階で拒否されるようにする
  - 結果値から指定フィールドの値を取り出す手段を用意する。結果種別に存在しないフィールドは値なしとする
  - 取り出した値はJSONのクォート・エスケープを施さない生の文字列とする
  - 出力形式の指定・テンプレート展開・複数フィールドの同時指定を受け付ける余地を作らない
  - 結果種別とフィールドの全組み合わせについて、値と「値なし」が単体テストで確認できる
  - _Requirements: 2.2, 2.5, 2.7_

- [x] 5.2 結果種別から終了コードを決める規則を実装する
  - クリックと返信を0、アクションを基準値とアクション番号の和、却下と時間切れをそれぞれ専用の値とする
  - 終了コードの数値はすべて既存の定数群と同じ場所に定義し、他の場所に直接値を書かない
  - 既存の予約コード (通知未許可・環境エラー) と衝突しないことを不変条件とする
  - 5種の結果すべてについて終了コードが確認でき、予約コードを返さないことがテストで固定される
  - _Depends: 5.1_
  - _Requirements: 1.1, 1.2, 1.3, 1.4, 1.6, 1.7_

- [x] 5.3 出力内容の決定を出力方針に従わせる
  - 出力方針を受け取り、フィールド指定があれば単一の生値を、なければ従来どおり結果JSON全体を出力内容とする
  - フィールドが結果種別に存在しない場合は「出力しない」を表現できるようにし、空行も書かないようにする
  - 出力方針を省略したときの結果が、変更前の実装と完全に一致することを事後条件とする
  - 終了コードの決定は、方針で有効化されている場合のみ結果種別に依存させる。それ以外は従来どおり0とする
  - 既定の出力方針での出力内容と終了コードが変更前と一致することを回帰テストで固定し、フィールド不在時に書き込みが発生しないことを確認できる
  - _Depends: 5.2_
  - _Requirements: 1.5, 1.8, 2.1, 2.4, 2.6_

- [x] 5.4 通知送信サブコマンドから出力方針を配線する
  - 終了コードの有効化フラグとフィールド指定の2オプションを追加する。フィールド指定には短縮形を割り当てない
  - 構築した出力方針を、通知の結果が確定する経路まで受け渡す
  - 2つのオプションの同時指定を検証エラーとせず、生値の出力と結果依存の終了コードが両立するようにする
  - 未知のフィールドが指定された場合は通知を配信せずに引数エラーとする
  - 実際の通知フローを模した結合テストで、方針の有無による出力内容と終了コードの差が確認できる
  - _Depends: 5.3, 4.1_
  - _Requirements: 2.3, 3.1, 3.2, 6.4_

- [x] 5.5 通知送信サブコマンドのヘルプに説明と使用例を加える
  - コマンド自体の説明と、代表的な使用例を表示する
  - 使用例として、完了通知・アクションボタンによる承認確認・返信テキストの取得の3種類を含める
  - すべての文言を英語で記述する
  - ヘルプの表示に説明と3種類の使用例が現れる
  - _Depends: 4.1, 5.4_
  - _Requirements: 7.2, 7.3, 7.4_

- [ ] 6. 既存コマンドの追随

- [x] 6.1 待機プロセス一覧の引数解釈を短縮形と単位付き指定へ追随させる
  - 一覧の対象判定を、タイトル指定の長短両形式で行う。短縮形のみで起動されたプロセスが一覧から漏れないようにする
  - タイトルの抽出も長短両形式に対応させる
  - タイムアウトの解釈を 1.1 の共有部品へ委譲し、通知送信側と同一の変換規則を用いる
  - テキスト表示のタイムアウトを経過時間と同じ人間可読の形式で表示し、機械可読出力では秒数のまま出す
  - 通知APIに依存しない状態を維持する
  - 短縮形のみで起動されたレコードが一覧に残り、単位付き指定が正しい秒数として扱われることを確認できる
  - _Depends: 1.1_
  - _Requirements: 14.1, 14.2, 14.3, 14.4, 14.5, 14.6, 14.9_

- [x] 6.2 待機プロセス一覧にプロファイルによる絞り込みを追加する
  - プロファイル名を指定したとき、該当するプロファイルのプロセスのみを一覧する
  - 指定された名前が命名規約を満たさない場合は、一覧を出力せずエラー終了する
  - 絞り込み指定時は既定バンドルのプロセスを対象から外す
  - 絞り込みの有無による一覧の差と、不正な名前の拒否がテストで確認できる
  - _Requirements: 14.7, 14.8_

- [x] 6.3 (P) 通知未許可時の案内に対象バンドルと設定場所を含める

## Implementation Notes

- Swift 6の並行性チェックは、非Sendableなクロージャを静的な格納プロパティ (`static let`) に保持することを拒否する。注入点は `static func` で提供する (既存の `ExitCoordinator.defaultWriter` / `ProfileDispatch.defaultExec` と同じ形)。クロージャ型に `@Sendable` を付けると、今度はテストが可変ローカル変数を捕捉して呼び出しを記録できなくなる (task 1.2)
- `@Sendable` なcompletionHandlerから結果を受け取るテストは、可変ローカル変数ではなくロック付きボックス経由で書き込む (`LaunchGuardTests.Recorder` と同じ形。task 1.3, 2.2)
- 本リポジトリのswift-format設定は `AvoidRetroactiveConformances` を有効にしている。外部型を外部プロトコルへ適合させる設計は `swift format lint --strict` で落ちる (task 2.1)
- `parseAsRoot` はパースの一環で `validate()` を実行する。起動ゲートで種別判定を行うと `validate()` が追加で1回走るため、`validate()` に副作用 (ファイル書き込み・ロック取得・標準入力の消費) を置いてはならない (task 3.2 以降の前提)
- Swift 6.3.3 は existential metatype を根とするキーパスで SIL 生成がクラッシュする。`configuration.subcommands.map(\.configuration.abstract)` が該当 (`subcommands` は `[any ParsableCommand.Type]`)。同じメンバーを for ループで読むぶんには問題ないため、ループで回避する (task 3.1)
- `decide` の分岐に端末接続の有無が入ったため、既存テストで案内の有無を検証する場合は `isStandardErrorTerminal` を明示すること。省略すると実行環境の tty 状態にテストが依存する (task 3.5)
- `NotifyCommand.parse()` を使うテストは `validate()` まで実行される。`-m -` のような端末判定を伴う入力を直接パースすると、端末から `swift test` を実行したときだけ落ちる環境依存テストになる。パース後にプロパティを差し替えるか、判定を注入して検証すること (task 4.4)
- `--image` に渡すパスはテストでも実在が必要になった (配信前検証)。実在するフィクスチャは `TestSupport.existingImagePath()` を使う (task 4.5)
- 新しいサブコマンド・オプションは、インストール済みバンドルを更新するまで実機では使えない。透過ディスパッチが旧バンドルへ引き継ぎ、旧バイナリが新しい構文を知らないため。`doctor` 自体も引き継がれるので、旧バンドルが残っている間は診断も旧バイナリで走る。端末ではバージョン不一致の note が更新を促す (task 7.2 実測: 旧 v1.0.1 バンドル + 新バイナリで `doctor` が notify として解釈され "Missing --title" になる)
